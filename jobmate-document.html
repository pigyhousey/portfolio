第二部分

3个关键产品决策

决策 1 模型选型——盲测而非默认最强
结论
生产模型应由数据决定，而非默认最强。质量最高的不是最贵的。
评测设计

需评测的3个模型：opus 4.8 / opus 4.7 / sonnet 4.6。

盲测机制设计：剔除模型身份、答案文件另存。

JD选取与打分规则：5个代表不同类型的差异化JD，按输出完整度、判断准确度、意图推断深度3个维度独立打分，并核算单次成本。

评测结果
sonnet 4.6 总分68（满分75），高于 opus 4.8 的57分、opus 4.7 的57分；输出结果最长（约为另外2个模型的1.8倍）、质量最高、单次成本最低。综合输出质量和成本，选用 sonnet 4.6 为生产模型。
决策 2 与AI的协作边界——CLAUDE.md
结论
AI工具不会主动区分"工程实现"和"产品决策"，边界必须由人写下来——保证每次对话都能被依据。
协作中遇到的真实问题
模型默认选用了最强的；页面布局方式没有询问就直接决定——它默认所有未指定的选择都是工程问题。
建立明确的协作机制
在 CLAUDE.md 文件中明确写出——涉及产品意图和决策的事情由人来决定，工程实现由 Claude Code 辅助。关键产品决策包括但不限于：模型选型、关键参数、Prompt内容、影响用户体验的决定等。口头约定靠不住，规则文件才能保证每次对话都有据可依。
决策 3 展示与隐私的取舍
结论
公开演示用示例数据并显式声明，真实数据密钥保护；单用户场景下不引入用户体系。
场景
产品链接发给招聘方点击查看——若使用个人真实使用数据则涉及隐私，若隐藏不展示则未能展现产品全部功能。
落实方案
为展示产品完整功能，用示例数据进行页面展示，并在最上方明显标注"数据为虚构的示例数据"；个人真实使用数据页面用密钥保护、单独入口进入，保护个人隐私且不影响正常使用；考虑到目前用户为自己，单用户场景下不引入复杂的用户体系。
第三部分

上线后的效果验证

上线前评测的是"输出质量"，而上线后评测的是输出到底对决策有没有用——输出可以质量很好但完全没起作用。三个发现指向同一件事：这个产品在回答一个我已经知道答案的问题。问题不在模型不准，而是产品站错了位置。

发现 1 匹配度指标不足以支撑投递决策
结论
匹配度指标能预测被否，但不能预测被选。
统计样本
144份（有反馈结果且为自主投递），剔除14份由对方主动联系并索要简历的样本。
数据解读
匹配度与明确拒绝存在弱相关（匹配度低的岗位对方更快给出明确否定），但由于样本中零正样本（即无一进入面试），该指标对"能否进入下一步"的预测力实际上无法被验证。两者叠加，它不足以支撑投递决策。
发现 2 AI评级比人更分散，且高档存在系统性上浮
结论
未做限制时，AI的评级比人更分散——高档源于"能力可迁移"的默认上浮，低档源于对硬门槛的机械扣分。
一致性分析结果
将AI分析的匹配度与人工预判评分进行一致性分析：AI评为"中高"的71份中有57份偏高，"中低"的74份中有24份偏低，而"中"的86份中高达84份与人工一致。
原因分析
AI敢给"中高"是因为它按"简历呈现的能力可迁移"产生了系统性上浮。这一偏差并未影响实际投递行为——当时投递覆盖了各档位，匹配度在当时是被记录的观察值，而非直接的投递依据。
发现 3 200+ 次无效建议
结论
不给模型"不需要做"这个合法选项，它就必然会输出建议，哪怕没有可做的。
分析结果
将232份AI给出的投递建议进行分类统计：中度（2—3小时）调整简历后投的建议共204份，总时长超过400小时，与实际可执行的情况完全不符，此条建议几乎没被执行。
原因分析
这不是模型的判断失误，而是提问方式决定的——Prompt v3 中明确要求它输出"改简历方案"，它就必然会输出，却并没有给它"不需要改"这个合法选项。
第四部分

Prompt v3→v4 的迭代与验证

6处核心改动
改动 1
硬条件匹配改为初筛门槛判断器——逐项核对硬门槛、判断是否有放宽表述，输出初筛通过概率与可行路径
改动 2
禁止"调整简历后可提升匹配度"的上浮逻辑——明确要求模型只基于简历当前呈现的内容评估，禁止以"能力可迁移"为由抬高判断等级
改动 3
新增人工预判输入——把人工预判的评分和简要理由输入作为喂给模型的信息之一，让模型进行校准，判断候选者是高估 / 低估 / 无需校正
改动 4
砍掉改简历模块并强化打招呼语——去掉 Prompt v3 中改简历模块，为模型明确打招呼语的使用场景并输出针对HR / 业务负责人的两版内容
改动 5
新增JD撰写者判断——新增一个模块分析JD是HR按照模板发布还是由业务负责人撰写，为后续打招呼语该用哪个版本提供依据
改动 6
公司画像去掉对候选者接受度推断、收窄至判断岗位角色形态——仅让模型根据JD分析该岗位实际需要什么样的候选者，去掉了对候选者接受度的推断
验证 让模型能输出"放弃"的前提
结论
让模型输出"放弃"的前提，不是允许它说不，而是给它一套可核对的判断标准。
实例对比
JD207 在 Prompt v3 版本中建议中度（2—3小时）改简历后投，而 Prompt v4 则在判断硬门槛时发现有3项不满足且无明显放宽表述，判断初筛通过概率低，建议放弃。
归因
Prompt v3 也提供了"不投"选项，但缺少判断依据，232次分析里只出现过3次；Prompt v4 把硬门槛拆成逐项可核对的清单后，"放弃"才成为一个有依据、可解释的结论。
二次修正 用户初判的理由会污染模型结论
结论
用户提供的判断理由会成为模型的前提，而不是被检验的对象。输入不足会让输出发散，输入带着倾向则会让输出收敛到那个倾向上——两者互为两面。
问题
JD200 的 Prompt v4 测试结果显示"候选人低估"（人工预判为中），但模型自己在各维度的分析中得出的是初筛通过概率低、契合度中低——前后矛盾。
归因
我给出的"合同场景有涉及"被模型接受为"基本准确"，一路传递到最终结论，即使模型自己在各维度分析中得出了相反的判断；同时，模块间的结论缺少一致性约束。
具体修正（迭代至 Prompt v4.1）
一是要求模型单独审查用户初判理由是否成立，不得笼统认可；二是要求最终结论与各模块判断保持一致，若存在例外必须写明理由并指出推翻了哪一条判断。
重测验证
重跑 JD200，结果改判为"候选人高估"，并明确指出高估来源是"场景名词重叠产生了关联感"。
